# 实体-组件-系统 (Entity-Component-System) 目录

## 职责

`ECS` 目录是游戏逻辑的核心实现。它遵循数据驱动设计的原则，将游戏对象（实体）的行为和状态分离，以提高代码的灵活性、可维护性和性能。

## 核心概念与文件

- **`EcsSystem.cs`**: 这是一个 `ModSystem`，是整个ECS框架的全局宿主和入口。它以单例形式存在，负责创建和管理 `EcsWorld`、`SystemManager` 等核心对象，并驱动整个框架的更新循环。
- **`EcsWorld.cs`**: ECS的“世界”，是所有实体和组件的中央容器。它负责创建/销毁实体，并使用**原型（Archetype）**机制高效地组织和查询实体。
- **`IComponent.cs`**: 一个标记接口，所有组件都必须实现它。**组件 (Component)** 是纯粹的数据容器，只包含状态，不包含任何逻辑（例如 `MovementComponent` 存有速度、目标位置等数据）。
- **`SystemInterfaces.cs`**: 定义了 `ISystem` 和 `IComponentSystem` 接口。**系统 (System)** 是纯粹的逻辑容器，它包含了处理组件数据的行为（例如 `MovementSystem` 会根据 `MovementComponent` 的数据来更新NPC的位置）。
- **`SystemManager.cs`**: 负责管理所有的 `System`，并在每个游戏帧调用它们的 `Update` 方法。它会利用 `EcsWorld` 的原型查询能力，确保每个 `System` 只运行在包含其所需组件的实体上，这是性能优化的关键。
- **`Archetype.cs`**: 原型的定义。一个原型代表了一组独一无二的组件组合。`EcsWorld` 通过它来对实体进行分组。

## 子目录结构

- **`/AI`**: 包含与AI决策相关的数据结构，例如 `Blackboard.cs`（黑板），它是一个临时的、状态内的数据存储，用于行为树节点间的通信。
- **`/BehaviorTree`**: 行为树的实现。行为树用于构建复杂的、模块化的AI逻辑，例如一个特定的攻击模式。
- **`/FSM`**: 有限状态机（Finite State Machine）的实现。FSM用于管理Boss的高阶状态，例如在不同的战斗阶段（Phase 1, Phase 2）之间切换。
- **`/Intents`**: （已废弃）旧架构中用于AI与系统通信的意图对象。在新架构中，这种通信应通过修改组件数据或发布事件来完成。
- **`/Interfaces`**: （已废弃）旧架构中用于定义组件接口的目录。在新架构中，组件是纯数据，通常不需要复杂的接口。
